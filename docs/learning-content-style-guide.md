# 渐进式教学内容规范

这套规范用于知识库正文。目标不是让文章“看起来完整”，而是让第一次接触主题的读者能够建立正确模型、跟踪一次真实运行，再按需进入实现细节。

## 核心原则

每篇文章都按下面的认知顺序组织：

```text
读者现在遇到什么问题
    -> 一句话核心结论
    -> 一个贯穿全文的最小场景
    -> 机制怎样一步步运行
    -> 为什么这样设计
    -> 常见误解和失败路径
    -> 进阶实现与取舍
```

不要按“术语词典”的顺序写文章。术语应在解释具体问题时自然出现。

## 建议骨架

正文优先采用以下结构。标题可以根据主题调整，但承担的教学职责不能缺失。

### 1. 先说结论

开头用三到六句话回答：

- 它解决什么问题；
- 最核心的运行关系是什么；
- 读完后读者应能解释什么。

不得在开头连续引入三个以上尚未解释的专业术语。

### 2. 一个最小场景

选择一个贯穿全文的例子。例子必须包含具体输入或初始状态，避免只罗列“玩家、敌人、子弹”等名词。

```text
不够具体：对象池可以保存子弹、特效和 UI。

足够具体：连续发射三颗子弹；前两颗命中后回收；第四次发射时复用第一颗子弹。
```

### 3. 先跑一遍

在完整定义和边界条件之前，展示一次从输入到结果的过程。每一步都回答：

```text
现在有什么状态？
执行了什么操作？
哪些数据发生变化？
为什么得到这个结果？
```

### 4. 再拆概念

读者已经见过一次运行后，再为各部分命名和定义。定义要回指前面的场景，不能只用另一个抽象词解释当前抽象词。

### 5. 回答自然追问

优先回答读者从最小场景中必然产生的问题。例如：

```text
系统怎样找到这些数据？
两组数组怎样保证不会错位？
中途删除一个元素会怎样？
什么时候不适合使用这种方案？
```

文章标题承诺的核心问题必须在前半篇得到回答。

### 6. 常见误解与失败路径

不要只列错误名称。每个重要错误至少给出：触发条件、错误结果、正确做法。

### 7. 进阶：实现差异与取舍

框架差异、标准边界、性能细节、并发和替代实现放在进阶区。明确区分：

- 为了理解概念必须知道的内容；
- 常见实现方式；
- 仅在设计框架或排查性能时才需要的内容。

## 写法要求

### 一段只推进一个认知步骤

避免在一句话中同时完成定义、限定、反例和实现差异。必要的严谨限定可以紧跟结论，但不要让限定淹没主线。

### 图和代码必须承担解释任务

代码块不是普通列表的装饰容器。普通并列信息使用项目符号或表格；代码块只用于代码、内存布局、状态变化和确实需要等宽对齐的流程。

代码示例优先满足：

- 能看出输入；
- 能看出关键状态；
- 能推导输出；
- 省略的框架细节已明确说明。

### 用数据快照代替模糊量词

“很多对象”“更快”“会搬迁数据”只能表达方向，不能帮助读者建立尺度感。重要机制应尽量给出可手算的数据例子：

```text
初始状态：具体有哪些值。
一次操作：读取和修改了哪些值。
结果状态：数据变成什么。
规模扩展：10 个与 10,000 个时，循环或存储怎样变化。
```

性能和内存示例必须标明是教学估算还是框架实测。估算要公开假设和计算过程；实测要说明框架版本、硬件、数据规模与测量方法。不要把示意数字包装成通用性能结论。

### 先使用稳定称呼，再补英文术语

首次出现时使用“中文作用（EnglishTerm）”，之后保持同一个简称。不要在同一篇文章中交替使用多个近义称呼。

### 完整性采用分层，而不是堆叠

文章应同时服务两种阅读：

- 主线阅读：只读前半篇就能建立可用模型；
- 深入阅读：继续阅读进阶部分，理解限制与实现取舍。

严谨不等于把所有例外都放在定义旁边。

## 完稿检查

发布前逐项回答：

1. 读者能否在一分钟内说出这篇文章解决什么问题？
2. 是否有一个包含具体状态变化的贯穿例子？
3. 标题承诺的核心机制是否在前半篇解释完毕？
4. 每个新术语出现时，读者是否已有东西可以和它对应？
5. 是否展示了至少一次输入到结果的完整运行？
6. 失败路径是否说明触发条件和可观察结果？
7. 进阶细节是否与入门主线明确分层？
8. 删除任意一段后若不影响理解，该段是否应该删除或移入进阶区？
9. 是否至少有一组能从输入手算到结果的数据快照？

## 基准文章

《ECS：实体、组件、系统与数据布局》作为工程概念类文章的基准：先用一个移动系统解释 Entity、Component、System，再解释 Query、Archetype、Chunk 和结构变化，最后介绍 sparse-set、generation 与并发边界。
